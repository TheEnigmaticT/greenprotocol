  **Product contract and non-negotiable rules**
  - A submitted analysis must remain usable if any nonessential source is slow, rate-limited, unavailable, unauthorized, malformed, or has no relevant result. GC.ai may return a clearly labeled partial/deferred evidence state; it must never silently present a degraded result as fully sourced or deterministic.
  - A source refresh must never mutate a saved analysis, accepted/rejected recommendation state, score, or audit trail. New data produces a versioned evidence update that a scientist can inspect and explicitly apply to create a new analysis revision/rescore.
  - Every imported record retains immutable source provenance: tenant, source system, source-account/connection ID, source record ID/URL where permitted, source revision/version, retrieval timestamp, source snapshot hash, importer version, normalization version, rights/access state, and original raw-payload retention reference or deletion reason.
  - Customer data is private to its tenant by default. It must not be exposed to another tenant, used to improve shared/public retrieval, sent to a model provider, embedded into a shared index, or used for training unless an explicit customer-approved policy says otherwise. Public/reference literature remains separately classified and cannot inherit customer-data visibility.
  - GC.ai is read-only for all 0.8.0 ingest sources. No ELN/task/journal/source record may be created, edited, tagged, deleted, or have a result written back. Any future write-back requires a separate, explicit authorization and audit design.
  - “Connectable” means an adapter exists, credentials/rights have been approved, schema mapping is validated, and a source-specific end-to-end fixture passes. Do not market or imply that GC.ai can ingest arbitrary sources without those conditions.
  - Ingestion is not a substitute for scientific validation. Retrieved records can rank, contextualize, or suppress recommendations; they do not establish that a proposed condition will work for the current experiment.

  **Canonical ingestion architecture**
  - Define a provider-neutral `SourceConnection` registry with tenant ownership, source class, authentication reference (never raw secret), approved scopes, rights policy, refresh cadence, health state, last-success cursor, failure/retry state, retention policy, and enabled/disabled state.
  - Define an immutable `SourceSnapshot` for every fetch/import. Store a content hash, source version/cursor, retrieval time, bounded raw-payload location or cryptographic deletion receipt, and connection/importer/normalizer versions. Deduplicate identical snapshots idempotently.
  - Define a versioned canonical `ExperimentRecord` / `EvidenceRecord` model rather than using a giant text file as the source of truth. Preserve structured fields, normalized text for retrieval, source pointers, and source-specific extensions without flattening away units, relationships, revisions, or attachments.
  - Define a staged pipeline: discover/request → authorize/validate → fetch/import → snapshot → parse → normalize → quality-check → quarantine or approve → index → associate to eligible analyses → expose reviewable update. Each stage emits a durable status, timing, error category, correlation ID, and audit event.
  - Run fetches and indexing as durable jobs, not in the analysis request path. Jobs must be idempotent, lease-safe, bounded in concurrency, observable, retryable with exponential backoff/jitter, and cancellable when a connection is revoked. Retriable source failures must not become permanent absence; confirmed absence must be represented separately from unavailable data.
  - Maintain a local tenant-scoped retrieval/index layer with structured filters plus lexical and semantic retrieval where appropriate. Search results must return the originating source record, snapshot/version, relevant fields/quoted span where applicable, similarity/applicability rationale, evidence state, and access check result.
  - Preserve a strict separation between raw source payload, normalized canonical record, derived search/index representation, and GC.ai-generated interpretation. Rebuild of a derived index must be possible from retained/approved snapshots without silently changing the source record.

  **Canonical customer experiment/ELN record**
  - Model at minimum: immutable GC.ai record ID; tenant; source connection; source experiment/task/document ID; source URL where available; title; author/operator; created/modified/retrieved times; revision/version; status; free-text procedure/notes; target/transformation where declared; materials with name, identity/CAS/SMILES if declared or resolvable, role, amount, unit, concentration, equivalents, supplier/batch where available; conditions including solvent(s), atmosphere, temperature, time, pressure, mixing/light and workup; outputs including product identity, yield, purity, selectivity, characterization/observation, failure mode, and disposition; attachment metadata; source hash; access/rights; normalization warnings; and source-specific extension data.
  - Preserve declared values exactly alongside any standardized value. Unit conversion, chemical identity resolution, inferred fields, missing fields, ambiguous mapping, and extraction failures must be explicit provenance-bearing derivatives, never replacements for the original declaration.
  - Treat attachments and instrument/raw-data files as references by default. Fetch/store their contents only when the tenant, access policy, file type, malware/size limits, and retention policy explicitly allow it. Record unavailable or skipped attachments visibly.
  - Define explicit record states: `discovered`, `fetched`, `normalized`, `needs_review`, `quarantined`, `indexed`, `superseded`, `deleted_at_source`, `access_revoked`, and `failed`. Do not index a record with unresolved ownership, cross-tenant ambiguity, unsafe content, or schema failure.

  **Source class 1 — rate-limited public/partner APIs**
  - Create a provider adapter contract for source discovery, record retrieval, pagination/cursor handling, source-specific rate limits, retry-after parsing, quota accounting, schema validation, normalized output, rights metadata, and provider health checks.
  - Cache successful results by canonical query/record identity and freshness policy. Before issuing a remote call, consult cache, negative/terminal-result state, and an in-flight deduplication key so one analysis cannot create duplicate retrieval load.
  - On HTTP 429/503/504, transport failure, provider outage, or quota exhaustion: enqueue/retry safely; retain the observed status and retry schedule; surface `deferred`/`unavailable` rather than `not found`; and avoid retry storms through per-provider concurrency and backoff controls.
  - On confirmed source absence, represent `not_found` with source, query, timestamp, and freshness/negative-cache policy. A later source refresh may legitimately overturn it.
  - Keep the existing PubChem chemical-reference recovery queue as a compatible implementation seed, but generalize it only after contract tests prove it supports tenant/source/job provenance and does not conflate unavailable, queued, and absent data.
  - Start with one rate-limited fixture/provider and document its exact quota, permitted fields, retention/attribution requirements, request cost, and acceptable-use constraints. Do not hard-code a generic “once a second/minute” rule across providers.

  **Source class 2 — customer experimental data and ELNs (DSV first)**

It must ingest only the DSV workspace/list/folder/document scope explicitly selected during setup; credentials must not grant or exercise unrelated account/storage access.
  - Do not treat ClickUp free text as a complete ELN schema. Define and provide a DSV experiment-template/mapping guide identifying which ClickUp custom fields, task fields, comments/docs, and approved attachments map to the canonical experiment record. Require a visible completeness/quality warning when key chemistry fields are absent.
  - Initial synchronization must be bounded, previewable, and explicitly approved: display candidate record count, date range, selected locations, field map, attachment policy, estimated data volume, and data-use/retention policy before execution. Record the approving user and configuration snapshot.
  - Incremental sync must use provider IDs, modification cursor/version, source hashes, idempotent upserts, and an explicit deletion/revocation policy. A daily scheduled pull is acceptable for the first DSV pilot; prefer provider webhooks only after signature verification, replay protection, and reliable recovery reconciliation exist.
  - Preserve source revisions. If a ClickUp task changes, store a new snapshot/version and mark the old one superseded; do not overwrite the historical evidence that informed a prior GC.ai analysis.
  - Provide a connection health/status surface showing last successful sync, records discovered/fetched/indexed/quarantined, skipped attachments, schema-quality distribution, latest source error, retry time, and a safe manual refresh action subject to quotas.
  - Build the adapter boundary so a later ELN migration replaces only the source adapter/mapping. The canonical record model, evidence store, retrieval interfaces, scientist-review UX, and analysis-provenance model must remain unchanged.
  - Support a local/customer-controlled deployment option in which source snapshots, normalized records, indexes, and job state stay within the customer-controlled environment. Make any external model-compute call an explicit, separately configured dependency; do not imply that “local ingestion” automatically means “no data leaves the network.”

  **Source class 3 — licensed journals and search providers (POST-0.8 — contract only; does not gate the 0.8.0 release)**
  - Model every literature/search connection with its institution/license holder, permitted API/search scopes, permitted content types (metadata, abstract, full text, supplementary information), storage duration, embedding/indexing permission, citation/attribution requirements, export/reuse restrictions, and expiry/review date.
  - Do not scrape around paywalls, bypass access controls, reuse personal institutional credentials, or treat browser access as API/bulk-processing permission. A subscription or search-result view is not blanket permission to retain, embed, send to an LLM, redistribute, or train on full text.
  - Normalize retrieved material into source documents and bounded evidence units with DOI/identifier, authors, title, venue, publication date, rights state, query/retrieval time, source location/page/section where available, quoted/extracted span, parsing warnings, and applicability caveats.
  - Keep bibliographic metadata, rights-cleared full text, customer-provided documents, and model-generated summaries in distinct stores and retrieval policies. A source may be citeable while its full text is unavailable for local retention.
  - Require human/adjudication status before a literature unit can be presented as direct support for a recommendation. Candidate retrieval may assist a scientist or model only with the evidence state plainly labeled; it must not be promoted automatically to validated support.
  - Begin with one rights-cleared source/API fixture and one no-permission/expired-permission failure fixture. Broader generalized literature ingestion remains constrained by the evidence-platform rights/provenance requirements; do not let this card bypass them.

  **How ingested data may influence GC.ai**
  - Use eligible customer experimental history to retrieve comparable precedent and influence recommendation ranking/applicability: for example, prior DSV observations that a solvent/atmosphere/substrate class achieved acceptable yield or failed under named conditions.
  - Never silently fold local historical outcomes into deterministic green-principle scores. A historical yield, purity, condition, or result can be an explicitly selected `declared local evidence` input or a separately displayed comparator/benchmark, with sample count, similarity basis, range, source IDs, and uncertainty.
  - Require an inspectable applicability rule before asserting that an imported experiment is comparable: chemical/reaction identity where available, transformation/role similarity, substrate/process context, conditions, scale, quality/completeness, source recency, and user/tenant-selected constraints. When comparability is weak, say so and do not use it as supporting precedent.
  - Retrieval should be able to rank, contextualize, challenge, or suppress a recommendation. It must not claim experimental validation, causality, or a guaranteed outcome from similarity alone.
  - The analysis UI must distinguish: `declared local evidence`, `public/source evidence`, `calculated`, `benchmark-derived`, `model-inferred`, `deferred`, `unavailable`, and `not found`; explain the difference between unavailable data and evidence that contradicts a recommendation.

  **Scientist UX and analysis lifecycle**
  - During analysis, show source-specific status without blocking core scoring: available, searching, queued/deferred with retry time, partially available, unavailable, unauthorized, no results, or failed. Provide a recoverable action and correlation/reference ID rather than a generic stream failure.
  - When a completed job adds potentially relevant material, show an explicit non-destructive update notice identifying source, record/evidence count, retrieval time, and why it may matter. Offer `Review evidence`, `Create updated analysis`, and `Dismiss`; never auto-rescore or auto-replace the existing analysis.
  - The evidence-review view must reveal record/source provenance, relevant declared fields or cited excerpt, source version, import time, access state, applicability/similarity explanation, normalization/extraction warnings, and whether the item influenced ranking, was merely considered, or was excluded.
  - An updated analysis must create a new revision linked to the prior analysis, preserve before/after score and recommendation differences, identify the exact newly eligible evidence, and retain the user who requested the refresh. Accepted/rejected states are copied only as clearly labeled prior decisions, never treated as approval of revised recommendations.
  - Provide user/operator controls to disable a connection, revoke access, pause sync, request deletion where policy permits, and inspect import activity. Revocation must prevent future retrieval and remove/restrict derived tenant indexes according to the documented retention policy.
