# v0.7: Two-Pass Retrieval Re-evaluation Pipeline

## Overview

The v0.7 release introduces a **two-pass re-evaluation pipeline** that critically validates each recommendation against retrieved literature before displaying it to users.

## Architecture

### Pass 1: Generate Recommendations (Phase 2)
1. Parse protocol (Phase 1)
2. Evaluate all 12 Green Chemistry Principles in parallel
3. Generate initial recommendations with confidence levels

### Pass 2: Re-evaluate with Evidence (Phase 2.7)
For each recommendation:
1. **Retrieve literature evidence** from vector database
   - Query combines original chemical + alternative + rationale
   - Retrieve top 5 matches with threshold 0.3
   - Filter by principles and chemicals involved

2. **LLM re-evaluation** with structured output
   - System prompt provides original recommendation context
   - Retrieved literature snippets with similarity scores
   - LLM must assess evidence quality and context match
   - Output: `confirm`, `downgrade`, or `suppress`

3. **Apply re-evaluation results**
   - **Confirm**: Keep recommendation, optionally upgrade confidence
   - **Downgrade**: Lower confidence, add concerns to caveats
   - **Suppress**: Remove recommendation entirely (not shown to user)

## Key Features

### Conservative Evidence Assessment
The re-evaluation prompt enforces strict rules:
- Suppress or downgrade if evidence is insufficient or contradictory
- Don't fabricate support if literature doesn't mention the alternative
- Context matters: domain-specific chemistry must match
- Quantitative evidence (yields, selectivity) beats qualitative claims
- No literature found → downgrade confidence + flag for validation

### Evidence Quality Metrics
Each re-evaluation returns structured assessment:
- `supportsOriginalIssue`: Does literature confirm the problem?
- `supportsAlternative`: Does literature support the proposed alternative?
- `contextMatch`: strong | partial | weak | none
- `quantitativeData`: Presence of numerical comparison data

### Rationale Revision
The LLM updates the rationale to reflect what the literature **actually** says, not what was initially assumed. This prevents overconfident recommendations based on general knowledge.

## Cost & Latency Impact

### Measurement Approach

#### Per-Recommendation Metrics
- **Vector search latency**: Time for literature retrieval (~100-300ms per recommendation)
- **LLM re-evaluation latency**: Claude API call time (~2-5s per recommendation)
- **LLM tokens**: Input (~1500-2500) + Output (~200-500) per recommendation
- **Total per-rec latency**: ~2.5-5.5s (serial processing to avoid rate limits)

#### Analysis-Level Metrics
- **Total re-evaluation time**: `num_recommendations × avg_per_rec_latency`
- **Total LLM cost**: `num_recommendations × (input_tokens × $0.003/1M + output_tokens × $0.015/1M)`
- **Recommendation suppression rate**: `suppressed / total_recommendations`

### Logging
All re-evaluation calls log:
- Start timestamp and recommendation identifier
- Literature match count
- Re-evaluation action (confirm/downgrade/suppress)
- Revised confidence level
- Elapsed time

Console output example:
```
Phase 2.7: Re-evaluating 8 recommendations against literature...
Phase 2.7: [1/8] Re-evaluating Dichloromethane...
Phase 2.7: Found 3 literature matches for Dichloromethane
Phase 2.7: CONFIRMED Dichloromethane (confidence: high)
Phase 2.7: [2/8] Re-evaluating Chloroform...
Phase 2.7: Found 1 literature matches for Chloroform
Phase 2.7: DOWNGRADED Chloroform (confidence: medium)
Phase 2.7: [3/8] Re-evaluating Benzene...
Phase 2.7: Found 0 literature matches for Benzene
Phase 2.7: SUPPRESSED Benzene — No literature support found; context mismatch
Phase 2.7 complete: 5 confirmed, 2 downgraded, 1 suppressed, 0 failed
```

### Statistics Tracked
Returned in `AnalysisResult.reevaluationStats`:
```typescript
{
  confirmed: number    // Recommendations validated by literature
  downgraded: number   // Confidence reduced due to weak evidence
  suppressed: number   // Recommendations removed entirely
  failed: number       // Re-evaluation API failures (kept original)
}
```

## Monitoring & Alerts

### Production Metrics
- **Re-evaluation latency P50/P95/P99**: Alert if P95 > 7s
- **Suppression rate**: Alert if > 40% (suggests poor initial recommendations)
- **Failed re-evaluations**: Alert if > 10% (API issues)
- **Cost per analysis**: Alert if > $0.50 (token usage spike)

### Logs to Capture
- Phase 2.7 start/end timestamps
- Per-recommendation latency
- Literature match counts
- Action distribution (confirm/downgrade/suppress)
- Any error messages or fallbacks

## Rollout Plan

1. **Development**: Test with sample protocols, measure baseline metrics
2. **Staging**: Enable for test accounts, collect 100+ analyses
3. **Production Canary**: Roll out to 10% of users, monitor metrics
4. **Full Production**: Roll out to 100% if metrics acceptable

### Rollback Criteria
- P95 latency > 10s per recommendation
- Suppression rate > 50%
- Cost per analysis > $0.75
- User-reported accuracy degradation

## Future Improvements

### v0.8 Optimizations
