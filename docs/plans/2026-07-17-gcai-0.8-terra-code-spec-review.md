# GC.ai 0.8 implementation-readiness code/spec review

Date: 2026-07-17
Reviewer: Terra
Scope: current local `main` at `4db1d03` plus the uncommitted 0.8 brief and local implementation files. This review is read-only except for this report.

## Executive decision

**Decision: do not call 0.8 implementation-ready as a single release branch yet.** The repository has a credible 0.6/0.7 base: authenticated analysis persistence, parsed step data, deterministic core scoring, structured waste/process-burden data, citation objects, vector retrieval, two-pass re-evaluation, acceptance persistence, and an Evidence Atlas. Those are useful seams, not completion of the 0.8 requirements.

The release should begin with a narrow 0.8-A contract slice, then a score/evidence slice. The largest risks are not UI work; they are (1) making context/procedure type a complete persisted contract rather than a label, (2) correcting score/provenance contract drift, (3) preventing “citation present” from being mistaken for procedure-specific precedent, and (4) defining deterministic data requirements for cost/energy/export/import.

A local pre-existing worktree is not clean: `BACKLOG.md`, `package.json`, and `package-lock.json` are modified; several planning/scripts files are untracked. `main` is three commits ahead of `origin/main`. This review did not alter any of those files.

## Evidence base and current architecture

### What exists in executable code

1. **Persisted analysis envelope.** `gpc_analyses` stores `protocol_text`, `analysis_result` JSONB, and `impact_delta` (`supabase/migrations/20260222000000_create_gpc_analyses.sql`). `POST /api/analyze` writes the envelope; `GET/PATCH /api/analyses/[id]` loads and writes the entire `analysis_result` JSONB. This makes additive, backward-compatible analysis metadata feasible without a physical-column migration.
2. **Protocol parse and pipeline.** `lib/pipeline.ts` parses free text into `AnalysisStep[]`, calls the chemistry service, generates LLM recommendations, retrieves literature, deduplicates, re-evaluates, ranks, and assembles a revised protocol. The current parse contract is reaction-oriented but generic enough to begin type-aware parsing.
3. **Deterministic data.** The FastAPI service has unit conversion, P1 PMI, P2/P3/P5/P6/P11/P12 scoring, waste analysis, RCRA context, and keyword-derived process complexity. It is invoked from `lib/chemistry-service.ts` and `lib/pipeline.ts`.
4. **Evidence base.** `literature_precedents` has embeddings, bibliographic metadata, a snippet, principle/chemical arrays, and a similarity RPC. `lib/vector-search.ts` queries it; pipeline phases 2.5 and 2.7 attach citations and can confirm/downgrade/suppress recommendations.
5. **Review and procedure draft.** Recommendations carry a tri-state `isAccepted`; decisions persist via PATCH. `components/FinalizedProtocol.tsx` displays accepted/pending/declined states and a printable text draft.
6. **Provenance foundation.** `ScoreProvenance`, UI labels, a documented taxonomy, and unit validation utilities exist. The Evidence Atlas renders score provenance and labels model-inferred recommendations explicitly.

### What is only spec/backlog, not implemented

There is no analysis context, procedure type, mode profile, process-type rules, typed elimination recommendation, procedure export endpoint, PDF upload/extraction, target/structure/reaction input, patent-aware retrieval, yield/purity/time precedent schema, runtime/energy/cost proxy, or bounded chemical-structure search contract.

The plan’s 0.8 requirements appear as unchecked BACKLOG entries (lines 14–30), not implementation. Existing completion summaries overstate production readiness in places: the literature pipeline document itself says the migration/ingestion and a real analysis remain pending, while the 0.7 document lists integration and end-to-end validation as pending.

## Cross-cutting contract findings (must be resolved before feature slices)

### 1. Analysis context and procedure type have no representation

`AnalysisResult` lacks context/type fields; `ProtocolInput` submits only `{ protocolText }`; `/api/analyze` accepts only that value; `analyzeProtocol`, prompts, chemistry-service request, retrieval query, scoring, result UI, Evidence Atlas, and exports receive none. JSONB persistence makes storage easy, but a UI-only selector would be a false implementation.

**Recommended canonical contract:**

```ts
analysisContext: {
  mode: 'discovery' | 'development'
  procedureType: 'reaction' | 'formulation' | 'separation'
  selectionSource: 'user' | 'legacy-default'
  schemaVersion: 1
}
```

Put this in `AnalysisResult`/stored JSONB first; pass it as a typed argument through every stage. For legacy analyses, derive an explicit `legacy-default` (`development` + `reaction` is a reasonable compatibility default only if product approves it), visibly label it, and never imply the user selected it.

### 2. The provenance taxonomy is valuable but not end-to-end enforced

The canonical TypeScript union is correct (`lib/types.ts`), and `validate-provenance.ts` plus `ScoreCard`/`PrincipleSection` implement the intended vocabulary. But validation is not called on chemistry-service responses in `lib/pipeline.ts` or `/api/rescore`.

There is contract drift:

- `lib/chemistry-service.ts` still types `estimated` and `partial`, values excluded by `ScoreProvenance`.
- `services/chemistry/scoring/p1_waste_prevention.py`, `p6_energy_efficiency.py`, and `waste_analysis.py` emit `partial`/`estimated`.
- The Python `ScoreProvenance` enum excludes those values. The field validator is too late to reliably convert an invalid enum value, so actual service serialization may fail or drift depending on the code path.
- Waste-summary provenance is rendered from JSONB but is not validated against the canonical union.

**Gate:** reconcile service output and TypeScript types, validate at the server boundary, and create fixture tests for every state before 0.8 scorecard/cost work. Do not create a separate evidence vocabulary: retain the five score provenance states, and model recommendation evidence state separately and explicitly.

### 3. Process redesign has design intent but no implemented entity

`docs/v0.6-process-redesign-architecture.md` proposes `RedesignProposal`, impacted steps, delta metrics, and caveats. None is in `lib/types.ts` or pipeline output. Current recommendations are substitution-shaped (`original.chemical → alternative.chemical`), and the assembler explicitly describes all inputs as substitutions (`lib/prompts/assemble.ts`). The existing process-complexity and waste heuristics can identify burden; they cannot represent, score, or trace an actual operation elimination.

### 4. Existing process-complexity integration is incomplete

`services/chemistry/scoring/process_complexity.py` implements `score_process_complexity`, but `services/chemistry/main.py` calls only `analyze_complexity` for waste analysis and does not include the P13 score in `all_scores`. `lib/pipeline.ts` then searches deterministic scores for principle 13 and will not find it. Thus the Process Complexity UI path is currently effectively unreachable from the current service response. Also, `analyze_complexity` returns no `workflow_complexity`, although waste analysis attempts to read it.

### 5. The reference corpus is infrastructure, not validated precedent coverage

Vector retrieval is implemented, but evidence tier means only “citation array non-empty” (`deriveEvidenceTier`). It does not express direct versus indirect support, evidence count, applicability, paywall/access status, patent versus paper, quantitative outcome, or a source-page anchor. The current retrieval schema has no fields for transformation, substrate scope, procedure type, yield, purity, time, scale, route change, access status, or extraction page. Its exact chemical-array overlap filter may also reduce recall when an input uses aliases.

## Feature readiness matrix

### A. Persisted mode and procedure type — NOT IMPLEMENTED

**Current support**
- JSONB `analysis_result` and full-object PATCH can retain additive metadata.
- Parsed steps, chemistry subdomain, service request, prompts, retrieval, score card, Evidence Atlas, and printable procedure are existing propagation points.

**Exact seams**
- Types: `lib/types.ts` (`AnalysisResult`, `ProgressEvent` if context is surfaced during streaming).
- Input/UI: `components/ProtocolInput.tsx`, `app/analyze/page.tsx`, `app/analyze/[id]/page.tsx`.
- API/persistence: `app/api/analyze/route.ts`, `app/api/analyses/[id]/route.ts`; migration only if query/index requirements justify physical columns later.
- Pipeline/prompts: `lib/pipeline.ts`, `lib/prompts/parse.ts`, `lib/prompts/principles.ts`, `lib/prompts/assemble.ts`, `lib/prompts/reevaluate.ts`.
- Service/retrieval: `lib/chemistry-service.ts`, service `ScoringRequest`, `services/chemistry/main.py`, `lib/vector-search.ts`.
- Results/export: `components/ScoreCard.tsx`, `components/EvidenceAtlas.tsx`, `components/FinalizedProtocol.tsx`, `app/api/export/dozn/[id]/route.ts`.

**Dependencies / risks**
- Requires agreed safe legacy defaults and unsupported-state policy; no default should silently claim formulation/separation competence.
- Type affects scoring validity, retrieval filters, and generation guardrails, so adding it after scorecards will cause rework.
- Current parse accepts generic chemistry text. A procedure type must be user-selected initially, not model-guessed as authoritative.

**Recommended slice**
0.8-A1: make both selectors required for new analyses; persist one `analysisContext` object; display it on saved result/Evidence Atlas; thread it into pipeline calls and prompt headers, but retain existing reaction scoring with visible `not yet specialized` states for formulation and separation.

**Acceptance tests**
1. Submit each of six mode/type combinations; saved JSONB, GET response, results header, and Evidence Atlas all contain the exact selected values.
2. Spy/mock pipeline, retrieval, and scoring adapters to prove each receives the same immutable context object.
3. Load a legacy analysis: it remains readable, is marked `legacy-default`, and does not fail type validation.
4. Invalid/missing enum values return 400; the UI cannot submit without an intentional selection.
5. A formulation/separation request does not present reaction-only PMI/atom-economy metrics as valid; it shows an explicit unavailable/unsupported reason.

### B. Mode-specific scorecards — PARTIAL FOUNDATION, NOT IMPLEMENTED

**Current support**
- Deterministic scorecard preserves raw principle scores; P1 PMI details, P6 temperature deviation, waste analysis, process burden, and score provenance exist.
- `ScoreCard`, `EvidenceAtlas`, and `PrincipleSection` can render metadata/details.
- `projected-scores.ts` supports a limited accepted-substitution recalculation (P3/P5/P10/P12).

**Gaps**
- No mode profile, metric schema, weighting, Discovery metrics (yield/purity/elapsed time/step count), or Development runtime/energy/cost metrics.
- Current P6 is temperature-deviation only, not energy. Duration is parsed but never used by scoring.
- `projected-scores.ts` preserves P1/P6/etc. despite accepted changes and cannot represent elimination, changed equivalents, steps, or process operations.
- P1’s PMI may be calculated from stated/benchmark yield, but the numeric PMI is not a dedicated main scorecard metric; the backlog confirms the UI task remains open.

**Exact seams**
- Add a typed `ScorecardProfile`/`MetricValue` model in `lib/types.ts`, separate from raw `DeterministicScores`.
- Deterministic formulas: new service scoring module(s), `main.py`, service TypeScript response, `lib/pipeline.ts`.
- Profile rendering: new component composed in `app/analyze/page.tsx` and/or `ScoreCard.tsx`; full rationale in `EvidenceAtlas.tsx`/`PrincipleSection.tsx`.

**Dependencies / risks**
- First settle provenance drift and data availability semantics.
- “Purity” has no parsed field or validated calculation. It must be `Unavailable` absent a declared assay/purity value or specific precedent.
- Scores should not use opaque mode-dependent weights as a replacement grade. Preserve raw scores and publish formula/weights/inputs.

**Recommended slice**
0.8-B1: profile layer only, not a new composite score. Discovery shows declared/precedent-backed yield, purity, elapsed-time, and step-count cards; Development shows raw sustainability/waste cards plus runtime and energy as unavailable until required declared inputs exist. Include metric definition, unit, provenance, formula/assumption, and unavailable reason.

**Acceptance tests**
1. Same saved raw baseline renders unchanged in both modes; only profile visibility/ordering changes.
2. Discovery fixture with stated yield/purity/duration shows values as Declared; fixture without them shows Unavailable, never an invented number.
3. Development fixture with duration/temperature/equipment assumptions shows every input, formula and unit; missing inputs show Unavailable.
4. Profile fixtures verify each of five provenance states and UI copy.
5. Snapshot/contract test proves baseline deterministic score values are not overwritten by the profile.

### C. Elimination and process-simplification recommendations — PARTIAL SIGNALS, NOT IMPLEMENTED

**Current support**
- P1 waste analysis recommends consolidate wash/extraction or telescope/one-pot based on heuristics.
- Process complexity can count transfers, vessels, preps, purification keywords, and steps.
- LLM principles prompt includes broad route/waste language; existing recommendations identify a `stepNumber`, caveats, confidence, and evidence container.

**Gaps**
- `Recommendation` requires a chemical replacement. There is no `recommendationKind`, operation target, affected step set, expected metric delta, risk model, or no-safe-elimination result.
- No change-addressability: global string replacement in `build-finalized-protocol.ts` can replace every occurrence of a chemical, ignores operations/equivalents, and cannot safely apply a deletion.
- Existing process redesign doc is design-only; no `RedesignProposal` implementation.

**Exact seams**
- `lib/types.ts`; `PRINCIPLE_SCHEMA` and `ASSEMBLE_SCHEMA` in `lib/pipeline.ts`.
- `lib/prompts/principles.ts`, `lib/prompts/assemble.ts`, re-evaluation prompt/schema.
- Process modules (`process_complexity.py`, `waste_analysis.py`) and a new deterministic operation-delta module.
- `FinalizedProtocol.tsx`, `lib/finalized-protocol.ts`, recommendation cards/Evidence Atlas.

**Dependencies / risks**
- Requires a stable parsed-operation/step model, not text-only mutation.
- Dedup key is `step:original chemical`; it will conflate or mishandle operation recommendations without redesign.
- High scientific risk: “eliminate” must be framed as precedent/calculation/hypothesis and not as a safe drop-in change.

**Recommended slice**
0.8-C1: add `recommendationKind: 'substitution' | 'operation-reduction' | 'condition-reduction'`; support one operation-reduction subtype, `reduce-washes`, on one explicitly parsed workup step. Store target step, proposed change, expected benefit, uncertainty, evidence state, and a structured patch. Do not ship route elimination or generalized one-pot generation in the first slice.

**Acceptance tests**
1. A wash-heavy fixture produces either a typed `reduce-washes` candidate with target step and caveat or an explicit unsupported/no-evidence result.
2. Accepting it changes only the named operation in the structured procedure; declining/pending leaves it unchanged.
3. Two independent same-chemical recommendations cannot overwrite each other in deduplication.
4. A no-citation candidate renders “Model-inferred (no direct citation)” and cannot claim calculated yield preservation.
5. Citation-backed candidate links its reference and reports applicability caveats.

### D. Evidence counts, citations, and inference clarity — PARTIALLY IMPLEMENTED

**Current support**
- `Citation`, citations array, ACS formatter, DOI/URL rendering, `evidenceTier`, and explicit model-inferred/no-citation callout exist.
- Pipeline phases 2.5 and 2.7 retrieve, attach, and reassess; re-evaluation tracks support/context/quantitative-data internally.
- Citation unit/vector-search/pipeline-ranking tests exist.

**Gaps**
- No visible per-recommendation reference count.
- `reevaluationMeta` is written using `@ts-expect-error`, absent from `Evidence`, and not rendered. The most valuable evidence-quality data is discarded from the typed/UI contract.
- “Sourced” requires only one attached citation, not direct support; semantic retrieval can attach a paper even if the re-evaluation downgrades it.
- Dedup may retain only the winner’s evidence and alternate rationale; citations from merged recommendations are not deliberately merged.
- No access/paywall/missing-full-text status, source type, source page, citation-level claim linkage, or patent support.
- Ingestion scripts exist but migration/application and corpus population are explicitly still pending. No test verifies production corpus count or live citation links.

**Exact seams**
- `lib/types.ts` (`Evidence`, `Citation`, recommendation evidence status), `lib/pipeline.ts` phases 2.5/2.7/dedup, `lib/prompts/reevaluate.ts`.
- `components/PrincipleSection.tsx`, `components/AnalysisResults.tsx`, `components/EvidenceAtlas.tsx`.
- Vector schema/RPC and ingestion scripts for richer metadata.

**Dependencies / risks**
- Corpus deployment/quality is an operational dependency, not merely source code.
- Need a precise distinction: `reported-precedent`, `calculated`, `benchmark-derived`, `model-inferred`, `unavailable`; recommendation evidence status should reference, not duplicate, score provenance.

**Recommended slice**
0.8-B2: define `EvidenceAssessment` as a typed public object: `state`, `supportingReferenceCount`, `directness`, `applicability`, `quantitativeOutcomeAvailable`, `accessStatus`, `citations[]`. Populate it after re-evaluation; preserve it through dedup; render count and exact no-direct-citation/paywall text.

**Acceptance tests**
1. Zero, one, and duplicate citations render counts 0/1/1 respectively; duplicate DOI/source ID does not inflate count.
2. Citation-free inference renders the explicit no-direct-citation message.
3. A retrieved but context-mismatched reference yields `directness: indirect`/downgrade, not a “literature-backed” success claim.
4. Paywalled and missing-source fixtures render access state honestly.
5. Every displayed citation has a URL/DOI validation result; broken links are visibly unavailable, not hidden.

### E. Accepted-procedure export — PARTIAL UI DRAFT, NOT IMPLEMENTED AS EXPORT

**Current support**
- Acceptance/rejection is persisted in analysis JSONB.
- `FinalizedProtocol` displays a current/finished procedure and uses `buildFinalizedProtocol`; print is available.

**Gaps**
- No accepted-procedure export route, download format, deterministic manifest, citations, source/provenance, unresolved-assumption section, or trace from changed passage to recommendation.
- Assembly occurs before the user accepts anything and includes all final recommendations, so `analysis.revisedProtocol` is not an accepted-only artifact.
- Fallback text replacement is global and chemical-name based; it lacks exact spans and can produce unsafe accidental edits. It cannot represent removal, equivalents, duration, or operations.
- Existing `/api/export/dozn/[id]` is not this export and queries `analyses`, not `gpc_analyses`; it also lacks auth/ownership checks and is therefore not a reliable basis.

**Exact seams**
- Replace text substitution with structured patches in `lib/finalized-protocol.ts`.
- New authenticated `app/api/export/procedure/[id]/route.ts`; UI in `FinalizedProtocol.tsx`.
- Types for patch, export manifest, citations, assumption list.

**Dependencies / risks**
- Depends on typed recommendation kinds/patches and stable source step IDs.
- Must define export format first (plain text/Markdown is sufficient for 0.8; PDF generation is unnecessary scope).

**Recommended slice**
0.8-C2: authenticated `text/markdown` export of a deterministic accepted-only procedure. Include header (analysis ID/version/context/type), original source reference, revised steps, accepted-change table keyed by recommendation ID, unresolved assumptions/pending items, and citations. Do not attempt document-layout PDF export.

**Acceptance tests**
1. Saved analysis with accepted, declined, and pending recommendations exports only accepted patches; byte-stable output for the same saved state.
2. Each changed step links/keys to a recommendation ID and its citations/evidence state.
3. Pending/declined items appear only in an explicit review section, never applied.
4. Unauthorized/non-owner requests return 401/404; export route reads `gpc_analyses`.
5. A no-accepted-changes export is valid and labels the procedure unchanged.

### F. PDF procedure import — NOT IMPLEMENTED

**Current support**
- Free-text textarea and parser can consume corrected text.
- No PDF dependency appears in `package.json`; no upload route, storage layer, extraction code, page metadata, or review UI exists.

**Exact seams**
- New upload/import endpoint under `app/api/import/` and a new client import/review component adjacent to `ProtocolInput.tsx`.
- New types for document source, pages, extraction spans/confidence, and review corrections.
- Storage policy (temporary object storage or client-only parse) and authenticated authorization boundary.

**Dependencies / risks**
- Choose a text-PDF extraction library/service and verify server/runtime compatibility before package change.
- Scanned PDFs require OCR; do not silently treat OCR as text extraction. Supporting Information often has tables, schemes, multi-column layouts, and critical superscripts that need a review workflow.
- Need retention/privacy limits before uploading proprietary procedures.

**Recommended slice**
0.8-C3: text-based PDFs only, capped size/page count. Extract per-page text, show page-labelled editable draft, retain filename/page anchors and extraction warnings. Explicitly reject scanned/encrypted/unsupported files with a clear alternative (paste/OCR outside 0.8).

**Acceptance tests**
1. A fixture text PDF imports into editable draft with exact filename and source page labels.
2. Corrected draft is what `/api/analyze` receives; saved analysis retains source metadata.
3. Scanned, password-protected, malformed, oversize, and unauthorized uploads produce safe actionable errors and no analysis.
4. Extracted page anchors survive edit/reload/export.
5. A test verifies temporary source deletion/retention behavior according to the approved policy.

### G. Discovery precedent retrieval (yield, purity, time, steps; mechanochemistry and route optimization) — INFRASTRUCTURE ONLY

**Current support**
- Generic semantic retrieval and two-pass re-evaluation exist.
- `SearchResult` includes bibliographic metadata/snippet/similarity; prompt mentions quantitative data.
- Existing chemistry parse gives steps and durations; P1 has yield/benchmark logic. Process complexity, purification burden, and the 0.6 redesign architecture are related foundations.

**Gaps**
- Retrieval query does not receive mode/type or a target transformation. It searches chemical substitutions and principles.
- Corpus schema cannot store normalized yield, purity, elapsed time, step count, reaction/transformation, scale, substrate scope, procedure type, mechanochemistry conditions, route relation, or patent fields.
- No mechanochemistry search/extraction code, milling condition model, route-precedent model, or benchmark corpus. Both associated backlog items remain unchecked.
- The plan’s required distinction between reported precedent and predicted outcome is not encoded.

**Exact seams**
- Extend `literature_precedents` or (preferably) add a normalized `precedent_observations` child table keyed to source/section/page rather than overloading the embedding table.
- Extend vector RPC/search filters and ingestion extraction. New retrieval planner module called from `lib/pipeline.ts` phases 2.5/2.7.
- Add `PrecedentObservation` to types and display in Evidence Atlas/recommendation cards.

**Dependencies / risks**
- Requires curated/validated data; generic abstract similarity is insufficient for quantitative process claims.
- Patent access/licensing and paywall status must be addressed before promising patents.
- Mechanochemistry belongs here as a Discovery candidate class, not a separate autonomous route product. It needs explicit conditions (mill type, frequency, time, ball-to-powder ratio, additive, scale) and an applicability statement.

**Recommended slice**
0.8-D1: Discovery/reaction only. Curate a small, testable precedent fixture corpus with structured observations for one transformation family and one mechanochemical candidate. Retrieve by declared transformation plus alternative concept; return reported values with source/page and scope caveat. No cross-family extrapolated yield/purity claim.

**Acceptance tests**
1. A known reaction fixture returns a matching reported yield/time/step observation with DOI/URL, source page, conditions, and applicability caveat.
2. Same query in Development mode does not surface exploratory mechanochemistry as a recommended replacement without explicit constrained framing.
3. No matching precedent produces an explicit no-direct-precedent state; no numeric yield/purity is invented.
4. A route-level source identifies one-pot/telescoped procedural difference separately from a solvent substitution.
5. Mechanochemistry fixture includes milling time/frequency/ball-to-powder ratio/additive when source data contains them; missing fields stay unavailable.

### H. Development runtime, energy, and hazardous-waste cost proxies — PARTIAL INPUTS, NOT IMPLEMENTED

**Current support**
- Parsed temperatures/durations, quantities, chemical roles, waste mass/hazard segments, liquid burden, process burden, and P6 temperature severity exist.
- P1 PMI and ACS benchmark fallback are existing decision-support foundations.
- LLM tracing estimates model-call cost, but that is software operational cost, not process cost.

**Gaps**
- No runtime aggregation; no equipment/power/duty-cycle model; no energy units; no waste disposal rate/currency/location; no formulas, input provenance, or auditable assumptions.
- `waste_analysis.py` assumes 60% of handled liquid is discarded and emits legacy provenance strings; it is not a hazardous-waste cost proxy.
- P6’s temperature deviation should not be displayed as energy consumption.

**Exact seams**
- `AnalysisStep.conditions` must add/normalize duration, possibly equipment/process state and declared scale; parsing prompt/schema must support them.
- New service module `development_proxies.py`, service models/response, `main.py`, `lib/chemistry-service.ts`, `lib/types.ts`, pipeline, scorecard/Evidence Atlas.
- A versioned assumptions source (region/currency/date/rates) must be persisted with analysis, not read live at render time.

**Dependencies / risks**
- The product must approve a bounded proxy model and default geography/currency. Waste classification/cost is highly jurisdiction/vendor dependent.
- Do not call it LCA, TEA, disposal quote, or compliance guidance. A default rate must be benchmark-derived, never calculated.

**Recommended slice**
0.8-B3: Development/reaction only; report (a) declared elapsed runtime as hours, (b) energy proxy only when user declares equipment power and operating duration, and (c) hazardous-waste cost range only when hazardous waste mass and a selected versioned rate card are available. Otherwise show Unavailable. Persist formula, assumptions, currency, rate-card version, and provenance per metric.

**Acceptance tests**
1. Given duration + 0.5 kW equipment + duty cycle, energy is reproducible in kWh with formula and declared/calculated provenance.
2. Without power/duty cycle, energy is Unavailable—not inferred from temperature.
3. Given hazardous mass and approved rate card, output provides low/high currency range, region/rate-card/date, formula, and benchmark provenance.
4. Rate card or waste-class missing yields Unavailable with reason.
5. Re-loading saved analysis reproduces prior values after a rate-card update because inputs/version were persisted.

### I. Bounded target-structure/reaction search — NOT IMPLEMENTED

**Current support**
- `scoreProtocol` accepts optional `reaction_smiles`; P2 can use it, though the user path never collects or supplies it.
- Vector retrieval accepts only natural-language query plus principle/chemical filters.
- Chemical conversion resolves names to SMILES, but there is no user-supplied structure UI, validation, canonicalization, substructure search, or reaction search.

**Gaps**
- No target substance/transformation/material-outcome field, structure parsing, chemistry-service endpoint, schema/index, retrieval planner, or unsupported-state behavior.
- No route enumeration/retrosynthesis implementation; that is correctly a non-goal.

**Exact seams**
- New optional target contract in `ProtocolInput.tsx`, request validation in `/api/analyze`, types/context, and pipeline.
- Chemistry-service validation/canonicalization endpoint using existing RDKit deployment; retrieval planner and precedent schema.
- Do not overload `reaction_smiles` into a generic string without validation/versioning.

**Dependencies / risks**
- Requires a decision on accepted formats (first slice: reaction SMILES and controlled free-text transformation; SMILES as optional target substrate/product later).
- Structures are sensitive input and RDKit parsing/canonicalization must fail safely.
- Existing corpus cannot answer a structure query reliably without transformation/structure fields.

**Recommended slice**
0.8-D2: Discovery/reaction only. Accept either validated reaction SMILES or a controlled text transformation. Validate/canonicalize server-side; use it to constrain retrieval to curated precedent records. Return evidence-backed candidates only; explicitly reject invalid syntax and return no-match/unsupported states. Do not generate routes.

**Acceptance tests**
1. Valid fixture reaction SMILES is canonicalized and persisted; retrieval query includes its normalized identifier.
2. Invalid/malicious/oversize structure input returns 400 without invoking LLM/vector retrieval.
3. A matching curated precedent is returned with source/scope; an unmatched query says no precedent, not an invented route.
4. Formulation/separation type renders target-structure search unsupported in 0.8 rather than running reaction logic.
5. Tests prove no code path invokes retrosynthesis or returns an unbounded route list.

## Recommended release sequence and gates

1. **0.8-A1 — context contract (first mergeable slice).** Context/type selection, JSONB persistence, propagation, legacy behavior, visibly unsupported score states. No specialized scoring claims.
2. **0.8-B0 — correctness gate.** Reconcile Python/TypeScript provenance outputs, validate chemistry-service response, fix/verify process-complexity integration, and add service contract tests. This is a release blocker for all profile work.

## Final readiness conclusion

0.8 has a strong architectural starting point but is presently a **spec/backlog release**, not an implementation-ready feature set. Start with a shared persisted context contract and score/evidence correctness gate. Treat provenance, PMI, waste/process burden, process redesign, mechanochemistry, route optimization, and two-pass retrieval as one coherent analysis/evidence system; do not rebuild parallel schemas or confidence labels. The safe first user-visible value is a context-labelled analysis with honest unavailable states and inspectable evidence—not broad process redesign, PDF OCR, cost claims, or autonomous chemistry search.
